**What to build:** the SQL views that turn `request_logs` into aggregates, shipped as a new migration.

**Read first:** DB §8 (both views; cache hits excluded from stage latency), DB §5 (the grant comment), DB §10.

**Scope notes**
- A new file `backend/migrations/000N_dashboard_views.sql` (the next number). Never edit `0001_init.sql`.
- **Pitfall:** `GRANT … TO app` fails where the `app` role doesn't exist (local, CI). Guard it (e.g. only grant when
  the role exists) or move the grant into the 5.09 role runbook. Pick one, document it, and test both environments.
- Views never expose `question` or `ip_hash`.
- **Decided by the Author (2026-10-26):** migration `0005_dashboard_views.sql`; the daily view buckets by UTC day and
  adds `validation_failures`; a third, row-level view `v_request_metrics` (public columns only) for 8.02's windowed
  percentiles; the grant is guarded in a `DO` block (granted where `app` exists) and also in the DB §5 role block (a
  fresh environment creates the role after the migrations); a new `migrate.yml` (`workflow_dispatch`, `main` only)
  applies migrations to Neon. Details: DB §5, §8, §10, Tech §17.

**Acceptance criteria**
- [x] Integration tests: percentiles on known rows, cache hits excluded from stage latency, `source='eval'` excluded,
      no private columns in the views.
- [x] The migration applies cleanly on a fresh DB and on a DB at the previous version.

**Verify:** standard checks, then `uv run grounded migrate`.

**Stop and ask:** the schema change (always for a migration).

**Eval impact:** none.
