**What to build:** a daily workflow enforces the privacy retention rules and keeps the backend warm (NFR-2).

**Read first:** DB §9 (retention SQL: NULL question/ip_hash after 30 days, delete logs after 180 days, expired cache,
old usage, rate-limit windows older than 2 days since 5.01), PRD NFR-2, NFR-4, Tech §17 (60-day scheduled-workflow
caveat).

**Scope notes**
- A `grounded housekeeping` CLI command runs the DB §9 statements (owner connection) and prints the affected row
  counts. Integration-tested against the local DB with rows of each age. The workflow calls this command, so the SQL
  is tested, not buried in YAML.
- `housekeeping.yml`: a daily cron + `workflow_dispatch`. A keep-warm step `GET`s the backend `/readyz` (it touches the
  DB, so Neon wakes too).
- Tech §17 lists the workflows. Update it (the keep-warm is decided to live here, 2026-09-28).

**What the Agent delivered (prepare only, the Author's instruction 2026-10-11)**
- `grounded housekeeping [--dry-run]` (`infra/housekeeping.py`, `cli.py`): the five DB §9 statements in one
  transaction on the owner URL (`DATABASE_URL_DIRECT`, else `DATABASE_URL`, like `migrate`), the periods bound as
  parameters, one output line per rule with its row count and a total. `--dry-run` runs the same statements and rolls
  back, so the counts are the real ones and there is no second copy of the conditions. **Choice:** the periods are module
  constants, not `Settings` fields (NFR-4 and DB §9 define them as the privacy contract; a setting could only lengthen
  them), and `tests/unit/test_housekeeping_docs.py` keeps the module's SQL, its parameter table and DB §9 identical. No
  migration was needed: the DB §9 SQL works on the current schema.
- Integration tests (`tests/integration/test_housekeeping.py`, local pgvector only): rows of every age on both sides of
  each rule's boundary in all four tables, the exact right rows deleted or NULLed, the rest untouched, idempotent second
  run (0 everywhere), dry run counts equal the real ones and change nothing, a failing rule rolls all of them back, and
  the command's printed lines.
- `.github/workflows/housekeeping.yml`: daily cron (03:23 UTC) and `workflow_dispatch(dry_run)`; jobs `retention` (the
  guard step of `ingest.yml`, copied and pinned identical by a test, then the command) and `keep-warm`
  (`.github/scripts/keep-warm.sh`: `GET $BACKEND_URL/readyz`, 4 tries of 45 s, 10 s apart, bounded, red after the last).
  **Shipped disabled:** on a schedule both jobs run only when the repository variable `HOUSEKEEPING_ENABLED` is `true`
  (the `EVAL_RECORD_RUNS` pattern); a dispatch from `main` always runs. `BACKEND_URL` is a repository variable (public
  origin, not a secret); unset, keep-warm is a notice. `DATABASE_URL_DIRECT` reaches two steps only. No `environment:`,
  so an unattended run never waits for a reviewer. Tests: `tests/unit/test_housekeeping_workflow.py` (+ the secret list in
  `test_ci_workflows.py`), including the script run against a local HTTP server.
- Docs: Tech §17 (the row, the gate, the variables, the 60-day caveat), DB §9 (implemented), README limitations,
  AGENTS §10, PRD §9 row, and step 10 of the [Neon runbook](../../docs/runbooks/neon-production.md) (the Author's
  steps: `BACKEND_URL`, a dry run, a real run, then `HOUSEKEEPING_ENABLED`).
- Nothing was run against Neon or the live backend, no workflow was dispatched, and no secret or variable was created.
