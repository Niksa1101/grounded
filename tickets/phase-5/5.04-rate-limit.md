# 5.04 — Input limits and the rate limiter

> **Before you start:** read [AGENTS.md](../../AGENTS.md), the rules in [tickets/README.md](../README.md) (how to work a ticket, ticket types, [standard checks](../README.md#standard-checks)) and the phase notes in [README.md](README.md). Work only on this ticket.

> **Owner:** G · **Type:** Build · **Branch:** `phase-5/rate-limit` · **Blocked by:** 5.03 ·
> **Builds on:** 5.01 decision, 5.03 `ip_hash`

**What to build:** oversized or malformed input is rejected early, and each client (by IP hash) is limited per minute
and per day, with a clear 429.

**Read first:** Tech §12 (input limits: 3–500 characters after trimming, no control characters, 4 KB body; the rate
limit), Tech §13 (`rate_limited` 429 + `Retry-After`), DB §4 (outcome `rate_limited`), 5.01 decision.

**Scope notes**
- `infra/ratelimit.py` per the 5.01 decision (D31): **Postgres fixed-window counters**, DB §7.4. The minute window is
  counted first and the day window only for a request the minute window admitted. The window clock is the database's
  (`now()`), with an injected `now` in tests so they stay deterministic. A counter query that fails is an
  `internal_error`, not a pass (Tech §12). It runs before the answer-cache lookup (Tech §1).
- A **new migration `0003_rate_limit.sql`** with the table of DB §4 (planned there) and the `app` grant of DB §5. The
  5.01 decision approved this shape; show the DDL in the PR and ask again only if it deviates.
- Move the `Settings` default of `RATE_LIMIT_PER_DAY` from 30 to 20 (and `.env.example`, the Tech §4 table, the
  settings test); the demo values are 5 per minute and 20 per day.
- 429 carries the `Retry-After` header **and** `retry_after_s` in the body, in seconds to the end of the window that
  rejected (at most 60 for the minute, up to a day for the day window). The outcome is logged. **Eval mode bypasses
  the limiter:** with `settings.app_env == "eval"` the limiter is not consulted at all (Tech §15.6; 4.03 added the
  switch and `tests/support.py:EVAL_SETTINGS` for tests), so an eval run of 30+ questions is never answered with a
  429 from our own limiter.
- A body over 4 KB is rejected before JSON parsing (`bad_request`). Control characters are rejected (`bad_request`),
  and the question is trimmed before the length check.

**Acceptance criteria**
- [ ] Tests: the per-minute and per-day limits hit exactly at the configured counts; a new window starts at zero
      (injected clock); different IP hashes are independent; the minute-rejected requests do not touch the day counter;
      the input-limit cases.
- [ ] **Integration test (local pgvector DB) for atomicity:** N parallel requests of one IP hash at `limit − 1` →
      exactly one is admitted.
- [ ] The `app` role can run the upsert but cannot delete from the table (the grant is `SELECT, INSERT, UPDATE`).
- [ ] **Eval switch test:** with `EVAL_SETTINGS` (`APP_ENV=eval`), more requests than `RATE_LIMIT_PER_MIN` from one IP
      hash all succeed, and the same requests are limited under `APP_ENV=test`.
