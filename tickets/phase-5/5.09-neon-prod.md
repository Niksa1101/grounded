**What to build:** production Neon has the schema, a least-privilege `app` role, and an active index, all produced by
repeatable, reviewed steps.

**Read first:** DB §2 (Neon notes: pooled vs direct), DB §5 (roles and grants), DB §10 (production migrations from CI
or locally with the direct URL, never from the runtime), Tech §17 (`ingest.yml`), Tech §18 "Database — Neon".

**Scope notes**
- `ingest.yml`: `workflow_dispatch(ref, activate)` from `main` → migrate + ingest into Neon with `DATABASE_URL_DIRECT`. It
  prints the index stats. It **restores the embedding cache** with the keys and paths of `warm-cache.yml` / `eval-index`
  (without it, a full ingest takes two days of quota). `activate` defaults to `false`; `ref` is the FastAPI tag (empty =
  `FASTAPI_REF`).
- The `app` role and grants (DB §5) come from a documented one-time runbook, since the password comes from a secret
  manager, not from a migration. The Author runs it: [docs/runbooks/neon-production.md](../../docs/runbooks/neon-production.md).
  DB §5 now creates the role without a password (`CREATE ROLE app LOGIN;`, then `\password app`); the runbook's SQL is a
  copy of that block and `tests/unit/test_neon_runbook.py` keeps the two identical.
- The runbook covers: the secrets, the cache check, the workflow runs, `grounded index list`, create the role, the manual
  least-privilege checks, set Vercel's `DATABASE_URL` to the pooled URL as `app`, rollback, a checklist, and (last, optional)
  the repository variable `EVAL_RECORD_RUNS`, which the Author sets and the Agent never does. The role comes **after** the
  first workflow run because the grants name tables the migrations create.
- The migrations the workflow applies now include `0003_rate_limit.sql` (5.01, 5.04). The grants of DB §5 include
  `rate_limit_counters` (`SELECT, INSERT, UPDATE`), and the manual `app` check covers the upsert of DB §7.4.
- **Prepare only (the Author's instruction, 2026-10-11).** The Agent wrote the workflow, the runbook and the tests, and
  ran none of it against Neon, Vercel or GitHub (no secrets or variables set, no dispatch). The runbook's SQL (grants,
  the privilege table, the allowed and denied probes) was run once against a throwaway database on the local pgvector
  container, with the role dropped afterwards.
