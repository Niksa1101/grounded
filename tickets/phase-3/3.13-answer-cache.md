> **Builds on:** DB §4 `answer_cache`, 2.01 config hash, 3.12 logging

**What to build:** repeated questions are answered from Postgres without embedding, retrieval or LLM calls, and the
response says `cache_hit: true`.

**Read first:** Tech §11 (key, normalization, TTL), DB §7.2 (read/hit/write SQL rules: only valid outcomes, errors
never cached, off in eval), PRD FR-17.

**Scope notes**
- `infra/answer_cache.py`. Normalization: NFKC → lowercase → collapse whitespace → strip trailing punctuation (a pure
  function, table-driven tests). Reuse it for `question_hash` (3.12) so both agree.
- Key = sha256(normalized question | prompt_version | index_version_id | retrieval_config_hash | generator_model).
- The stored response **excludes per-request `meta`**. On a hit, `meta` is rebuilt (new `request_id`, `cache_hit=true`,
  real latency, zero tokens and cost for the hit).
- TTL from `ANSWER_CACHE_TTL_DAYS`, with `expires_at ≤ created_at + 30 days`. The hit counter update follows DB §7.2.
- Disabled when `APP_ENV=eval` (the switch is added now; the rest of eval mode comes in 4.03).
- Later, the budget (5.05) is **not** consumed on a hit. Leave the ordering in the pipeline so that holds.

**Acceptance criteria**
- [ ] Tests: hit → zero provider and embedder calls, `cache_hit=true` in the response and in `request_logs`; errors
      aren't cached; an expired row is a miss; a different prompt version is a miss; eval mode bypasses the cache.
- [ ] Normalization unit tests.

**Verify:** standard checks, and ask the same question twice locally (the second time `cache_hit: true`).

**Eval impact:** none.
