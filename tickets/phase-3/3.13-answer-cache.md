# 3.13 — Answer cache (Postgres)

> **Before you start:** read [AGENTS.md](../../AGENTS.md), the rules in [tickets/README.md](../README.md) (how to work a ticket, ticket types, [standard checks](../README.md#standard-checks)) and the phase notes in [README.md](README.md). Work only on this ticket.

> **Owner:** G · **Type:** Build · **Branch:** `phase-3/answer-cache` · **Blocked by:** 3.12 ·
> **Builds on:** DB §4 `answer_cache`, 2.01 config hash, 3.12 logging

**What to build:** repeated questions are answered from Postgres without embedding, retrieval or LLM calls, and the
response says `cache_hit: true`.

**Read first:** Tech §11 (key, normalization, TTL), DB §7.2 (read/hit/write SQL rules: only valid outcomes, errors
never cached, off in eval), PRD FR-17.

**Scope notes**
- `infra/answer_cache.py`. Normalization already exists since 3.12: `infra/hashing.py:normalize_question` (NFKC → lowercase →
  collapse whitespace → strip trailing *sentence* punctuation, table-driven tests in `tests/unit/test_hashing.py`). Import it for
  the cache key instead of writing a second one, so the key and `request_logs.question_hash` agree.
- Key = sha256(normalized question | prompt_version | index_version_id | retrieval_config_hash | generator_model |
  confidence_config_hash). The last part is new in 3.13 (it closes the PRD §12 item from 3.09: the stored answer
  carries server-computed confidence, so a changed `CONFIDENCE_*` weight must be a miss). Tech §11 and DB §7.2 say so.
- The stored response **excludes per-request `meta`**. On a hit, `meta` is rebuilt (new `request_id`, `cache_hit=true`,
  real latency, zero tokens and cost for the hit).
- TTL from `ANSWER_CACHE_TTL_DAYS`, with `expires_at ≤ created_at + 30 days`. The hit counter update follows DB §7.2.
- Disabled when `APP_ENV=eval` (the switch is added now; the rest of eval mode comes in 4.03).
- Later, the budget (5.05) is **not** consumed on a hit. Leave the ordering in the pipeline so that holds.

**Acceptance criteria**
- [x] Tests: hit → zero provider and embedder calls, `cache_hit=true` in the response and in `request_logs`; errors
      aren't cached; an expired row is a miss; a different prompt version is a miss; eval mode bypasses the cache.
- [x] Normalization unit tests (they exist since 3.12; extend them only if the cache needs a different rule, which would also change `question_hash`).

**Verify:** standard checks, and ask the same question twice locally (the second time `cache_hit: true`).

**Eval impact:** none.
