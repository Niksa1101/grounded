implementation needs except the query itself.

**Scope notes**
- File `retrieval/lexical.py`: an async `lexical_search(conn, question, *, index_version_id, k)` returning
  `list[RetrievedChunk]` with `fts_rank` (1-based) set, a contract docstring and `raise NotImplementedError`.
- DB §6.2 lists a `score` output, but `RetrievedChunk` has no FTS score field. Propose adding `fts_score` (or skipping
  it) and **ask the Author**, since it changes a shared type.
- Build a hand-made fixture index (a few dozen chunks with controlled words, headings and page intros) in the style of
  `test_dense.py`. Hybrid (2.05) reuses it, so put shared builders in `tests/support.py` or a fixture module.
- Spec tests to include (all integration, real pgvector):
  - **OR semantics:** a long natural-language question matches a chunk containing only some of its words.
  - **Stop-words only** (e.g. "how do I do it"): returns `[]`, no error.
  - **Weights:** a term in the breadcrumb (A) outranks the same term only in the body (B), all else equal.
  - **Ranking:** `ts_rank_cd` descending, ties broken by chunk id ascending (deterministic), `fts_rank` = 1..n.
  - **Filtering:** only the given `index_version_id`; `k` is respected.
  - **Hostile input:** a question with `'`, `:`, `&`, `|`, `!`, `(`, `)`, `\` and non-ASCII doesn't raise and doesn't
    change query semantics. This is where a hand-built tsquery breaks.
  - Stemming: "running" matches "run".
- Mark the failing tests `xfail(strict=True, reason="Author implements in 2.03")`.
- Don't give the SQL away in docstrings or tests. The DB §6.2 *approach* text is fine to reference.
