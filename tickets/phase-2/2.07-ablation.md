**What to build:** `grounded eval retrieval --config dense fts hybrid` produces the ablation table, and the `fts` and
`hybrid` rows are committed to the retrieval baseline.

**Read first:** Tech §15.2, §15.7, AGENTS.md §7, PRD §8 (targets and the "1 question ≈ 4 pp" granularity).

**Scope notes**
- `"hybrid"` is already in `RetrievalMode` (2.01): add its branch to `build_search` and `"hybrid"` to
  `_RETRIEVAL_MODES` in `cli.py`. `k` is `k_fused` (MRR is computed over the fused list).
- Two PRs are fine if the Author prefers: code first, then a Baseline PR titled
  `eval: update baseline (add fts and hybrid ablation rows)`. Numbers come only from `--write-baseline`.
- The PR description has the table (Recall@5/@10, MRR, nDCG@5/@10, `n`) for all three configs, a per-question diff of
  where hybrid wins or loses against dense (from the results files), and an honest reading of the numbers. Differences
  smaller than one question are called noise.
- **Exit criterion:** hybrid ≥ dense on Recall@5 **and** MRR. If not, the reason goes in the PR and README "Evaluation",
  backed by per-question evidence (e.g. FTS isn't BM25, Tech §20). Tuning K or weights against the golden set to make
  the numbers look better is not allowed unless the PR says so (AGENTS.md §13).

**Acceptance criteria**
- [ ] The `hybrid` mode is wired and tested (unit + integration on the fixture).
- [ ] `eval/baselines/retrieval.json` has `dense`, `fts`, `hybrid` rows written by the tool.
- [ ] Before/after table with `n` in the PR. The Author approved the baseline change.
- [ ] The README "Evaluation" section shows the ablation table, copied from the baseline file.

**Verify:** standard checks, then `uv run grounded eval retrieval --config dense fts hybrid --write-baseline`, and
check `git diff eval/baselines/`.
