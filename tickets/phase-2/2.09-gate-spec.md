**Scope notes**
- File `evals/gate.py`: a pure `evaluate_gate(...)` → a `GateReport` (status `pass | fail | inconclusive`, rows
  metric / baseline / current / Δ / threshold / ✅❌, `n`) with a stub. The Markdown rendering and the CLI exit code
  (0 pass/inconclusive, 1 fail) are boilerplate the Agent writes, since they don't decide anything.
- Add thresholds to `RetrievalBaselineEntry` (Tech §15.7 says thresholds come with this gate), e.g. per-metric rules
  of the form "≥ baseline − tolerance". Adding thresholds to the committed file is a **Baseline** change: a separate
  PR `eval: update baseline (add retrieval gate thresholds)`, with Author approval.
- Which configs are gated: the ones that carry thresholds in the baseline (initially `hybrid`). Others are reported
  only.
- Spec tests (pure, table-driven): equal → pass; a drop exactly at the tolerance → pass; a drop just past it → fail;
  one failing metric fails the suite; a baseline config missing from the results → fail with a clear reason; a golden
  set version, **golden-set sha256** or index config hash that differs from the baseline → the Author decides between
  error and fail (write the test once the Author chooses); `n` shown in the report.
- **Required baseline fields:** after R.03/B.01 every row carries `golden_set_sha256` and `git_dirty`. In this ticket
  they become **required** in `RetrievalBaselineEntry` (no longer `| None`), and the gate rejects a row without them.
- Update the AGENTS.md §3 table: `gate.py` becomes "retrieval part Phase 2, generation part Phase 4".
