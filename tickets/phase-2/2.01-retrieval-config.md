# 2.01 — `RetrievalConfig` and its hash

> **Before you start:** read [AGENTS.md](../../AGENTS.md), the rules in [tickets/README.md](../README.md) (how to work a ticket, ticket types, [standard checks](../README.md#standard-checks)) and the phase notes in [README.md](README.md). Work only on this ticket.

> **Owner:** G · **Type:** Build · **Branch:** `phase-2/retrieval-config` · **Blocked by:** R.07 ·
> **Builds on:** `settings.py` (retrieval fields), `evals/retrieval_runner.py`, `schemas/eval.py`

**What to build:** retrieval settings become one frozen `RetrievalConfig` value object with a stable hash. Every
retrieval eval run records which config produced each result. Later, the same hash goes into request logs, the answer
cache key and `eval_runs`.

**Read first:** Tech §4 (last paragraph: `RetrievalConfig`, `retrieval_config_hash`), Tech §7, Tech §11 (cache key),
Tech §15.2 (results file), DB §4 (`request_logs.retrieval_config_hash`, `answer_cache.retrieval_config_hash`).

**Scope notes**
- Lives in `retrieval/config.py`. It is built from `Settings` (`k_dense`, `k_fts`, `k_fused`, `k_context`, `rrf_k`)
  plus the **mode** (`dense | fts | hybrid`, later `hybrid_rerank`). Settings stay the only env reader.
- The hash is sha256 of a **canonical JSON** (sorted keys, no whitespace variance), like
  `ChunkingConfig.canonical_json()` in `ingest/types.py`. Mirror that style.
- Leave room for rerank fields (`rerank_provider`, `rerank_model`) so Phase 6 changes the hash when rerank is on.
  Whether they belong in the hashed JSON now is a review question for the Author.
- The results file records the config and its hash per config (`RetrievalConfigResult`).
- **Baseline schema (decided 2026-09-29):** `retrieval_config_hash` is an **optional** field on
  `RetrievalBaselineEntry`. The committed `dense` row doesn't have it, and B.01 fills it in. Never hand-edit the file.

**Acceptance criteria**
- [ ] `RetrievalConfig` is frozen, built from `Settings` + mode, with `canonical_json()` and `config_hash`.
- [ ] Unit tests: the same inputs give the same hash; changing any field changes it; key order doesn't matter.
- [ ] `grounded eval retrieval` writes the config and hash for each config into the results file.
- [ ] No behavior change in dense results: a re-run gives the same metrics as a run over the same active index before
      this change (not the committed baseline: R.07 changes the index, and B.01 regenerates the row).

**Verify:** standard checks, then `uv run grounded eval retrieval --config dense`, and compare the metrics with
a run over the same active index made before this change.

**Stop and ask:** nothing open; the baseline-schema question is decided (above).

**Eval impact:** none (bookkeeping only; metrics must be identical).

**Docs to update:** Tech §4 (list the config fields), Tech §15.2 (results file fields).
