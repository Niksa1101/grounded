**What to build:** every PR and every push to `main` runs the retrieval eval against a freshly ingested service DB and
is **blocked** when the gate fails.

**Read first:** Tech §17 (`ci.yml` retrieval-eval row, cache key, secrets), 2.08 decision, DB §2 (CI database),
Tech §5.1 (the corpus clone is cached too).

**Scope notes**
- A new `retrieval-eval` job in `ci.yml` with the same pgvector service image and the same action versions as the
  `backend` job. Steps: restore `.cache` (per 2.08), `grounded migrate`,
  `grounded ingest --ref $FASTAPI_REF --activate` (zero embedding calls when warm),
  `grounded eval retrieval --config dense --config fts --config hybrid --out …`, `grounded eval gate …`, the Markdown report written
  to `$GITHUB_STEP_SUMMARY`, and the results JSON uploaded as an artifact.
- The gate's exit code decides the job's result. An infra failure (cache miss + quota) must be distinguishable from a
  quality fail, as decided in 2.08.
- Per the 2.08 decision (PRD D45, Tech §17): two caches with `actions/cache/restore` in PR jobs (no save); `main` pushes
  save with `actions/cache/save` `if: always()`. Add `.github/workflows/warm-cache.yml` (`workflow_dispatch`) and the
  distinct infra exit code for a quota/no-key miss (needs a small CLI change). The Author runs the warm-cache workflow on two
  consecutive days before this job can go green.
- Permissions stay minimal (`contents: read`). Secrets only for same-repo PRs (Tech §17).
- Making the job a **required status check** on `main` is a GitHub setting the Author changes.
