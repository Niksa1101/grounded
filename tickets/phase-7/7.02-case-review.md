# 7.02 — Review sheet for the router cases

> **What this is:** the material for the one open criterion of [7.02](7.02-router-spec.md): "The Author has reviewed
> and extended the cases". The Agent prepared it on 2026-10-15 so that the review takes about an hour. It changes no
> test and no code. **The ticking, the decisions and the new cases are the Author's.**
>
> Read first: [Tech §10](../../docs/Tech.md#10-provider-router-fallback-and-circuit-breaker-a) (the event → action table and
> the contract), [PRD D57](../../docs/PRD.md) (b: timings, c: no caching of fallback answers, d: unbuildable fallback)
> and the module docstring of `backend/src/grounded/generation/router.py`.

## 1. How to use this sheet

1. Start with section 4 (the decisions, about 20 minutes): they are the points where the Author's call changes behavior.
   Then walk the table of section 2 group by group; the groups follow the Tech §10 rows, so each one is "do I agree
   that this is what the row means". Fill the last column of each row with `ok`, `change` or `add` (and a note).
2. Add or change a case in the file the row names (`S` = `test_router.py`, `R` = `test_router_robustness.py`,
   `V` = `test_router_review.py`; all three import the helpers of the first: `Probe`, `Rig`, `trail`, `limited()`,
   `timeout()`, `down()`; the docstring at the top of `test_router.py` says how to script a case in three steps).
3. Section 3 lists cases the Agent thinks are missing or weak, each verified against the test bodies. Section 5 says
   what to tick when you are done.

Run the router tests, and list them (231 collected: 150 in `test_router.py`, 33 in the robustness file, 48 in the
review file; they are 89 + 19 + 23 = **131 test functions**, the rest are parametrized cases, shown as "(n cases)"):

```bash
cd backend && uv run pytest tests/unit/test_router.py tests/unit/test_router_robustness.py tests/unit/test_router_review.py -q
```

```bash
cd backend && uv run pytest tests/unit/test_router.py --collect-only -q
```

```bash
cd backend && uv run pytest tests/unit/test_router.py -k "half_open" -q   # one group by a word of its names
```

state machine on its own, without the router. Every router case runs on scripted fake providers and a hand-moved clock.

## 3. Candidate extra cases

Only gaps verified by reading the three files (and `grep` for the others). "Router level" means through
`ProviderRouter.generate`; the state machine alone is covered where noted. None of these needs a change to `router.py`.

1. **A half-open trial that gets a 429 (router level).** The tests that hand out a trial answer ok, answer bad output
   (R, ending in a hook error), time out, are rejected, are cancelled or hit a hook error;
   `a_trial_that_gets_a_429_opens_for_the_given_seconds` is the state machine alone. The likeliest real sequence (Gemini per-minute 429, open 60 s, the trial is 429 again, possibly with another
   Retry-After, or a daily quota) is not run through `_tell_breaker`'s TRIAL path. Rationale: one parametrized case
   (`limited(30)`, `limited(None, quota=True)`) pins "reopen with the new plan, fresh timer, fall back in the same call", and
   the Tech §10 words "re-probed via half-open" for a quota whose reset is not derivable (900 s).
2. **Bad output on the half-open trial, asserted directly.** Decision 4.1 says it closes the breaker. Today it is pinned
   only through `a_retry_user_error_after_a_trials_bad_output_leaves_nothing_claimed` (whose point is the hook error) and in
   the random traffic. Rationale: it is the decision you are most likely to flip, so it deserves a case whose name says it:
   trial answers bad, bad, groq answers, gemini is `CLOSED`, the next request calls gemini.
3. **Both entries half-open with their trials held: `retry_after_s` is `None`.** The cases cover "trial in flight plus an open
   breaker" (the minimum) and "trial in flight plus a closed breaker" (`None`); the combination where nothing is closed,
   nothing is open and both trials are held is the `min(..., default=None)` path of `_retry_after_s`, and no body reaches
   it. Rationale: a 503 with no `Retry-After` is the intended answer there; nothing says so.
4. **The cap boundary and the `derived` field in the log.** `retry_after_s == BREAKER_MAX_RETRY_AFTER_S` (3600) should be
   `retry_after`, not `retry_after_capped` (the code says "a wait equal to the cap was not cut"); the cases use 30, 0.5,
   7200 and inf. And the log's `derived` is only asserted for `retry_after`, `default` (failures) and `quota_reset`, so
   `retry_after_capped` and the 60 s default of a per-minute 429 are checked in the pure `open_plan` only. Rationale: these are
   the first values a real Gemini or Groq 429 will show in the log (PRD §12 item 3).
5. **The `before_call` refusal on a retry, at router level.** `a_before_call_error_propagates...` refuses the fallback's
   call, and `a_refused_retry_has_reserved_nothing_for_itself` is about the deadline. The budget refusing the retry (first
   call reported, no retry call, error unchanged, breaker closed) is covered only in the pipeline
   (`tests/integration/test_budget.py::test_a_retry_that_finds_the_budget_gone_ends_in_budget_exhausted`).
   Rationale: low; it is a different line of `_route_entry` than the one the router tests use.
6. **The Settings to router seam for `inf`.** `BREAKER_*_S=inf` passes `Settings` (it requires `gt=0`, and pydantic accepts
   inf; NaN is rejected) and then `BreakerConfig` raises `RouterConfigError`, at startup when the pipeline builds the router.
   The `BreakerConfig` docstring says "(`Settings` enforces the same)", which is true for 0 and negatives only (checked with
   `make_settings(breaker_max_retry_after_s=math.inf)`). No test pins either outcome. Rationale: pick "fail at startup with
   this message" or "refuse in `Settings`" (the second is a Settings change, not in the router).
7. **`log_extra` is copied.** `_checked_log_extra` copies the mapping "so a caller mutating its dict later changes nothing";
   no test mutates it. Rationale: low; it is a private helper's promise, not in the contract text.
8. **Three or more entries.** Only `bad_output_and_a_rejection_are_not_causes` uses three providers (and it never has one
   answer). A list where the middle entry is skipped and the last answers (`fallback_used`, trail order) is not run.
   Rationale: low; production has two entries and `GENERATOR_PROVIDERS` is validated for duplicates elsewhere.

Areas where **none were found**: the retry rule (one retry, original message on the fallback, non-retryable output), the
Gemini midnight arithmetic (DST and the repeated hour), the window and open-time boundaries, "exactly one trial" under
concurrency, trial release on every exit path (cancellation, hook errors, adapter bugs, 12 seeded random runs), the
deadline gate order against `before_call`, the straggler rule and its documented limit, `causes` and the narrowed
`retry_after_s`, and breakers off.
