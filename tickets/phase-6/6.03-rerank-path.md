**What to build:** with `RERANK_PROVIDER=cohere`, the top `K_FUSED` candidates are reranked to `K_CONTEXT`. Any
problem (error, 429, cap) falls back to RRF order, and the request still succeeds.

**Read first:** Tech §8 (guard, cap, degradation, the error codes: all decided in 6.01), Tech §6 (sequence, rerank
timeout `RERANK_TIMEOUT_S` 3 s), Tech §14 (the rerank price rows), DB §7.1 (`rerank_calls` uses the same atomic pattern),
PRD FR-6 and D55.

**Scope notes**
- **From 6.02:** `runtime.build_reranker(settings, stack)` builds the reranker (`None` when `RERANK_PROVIDER=none`; it
  refuses a missing key or model; outside prod it adds the SQLite cache), `Reranker.rerank(query, chunks, top_n)` returns
  the best `top_n` with `rerank_score` set and raises typed provider errors, `rerank_error_code(error)` gives the
  `rerank_error` code (`cap_reached` is yours: the cap is checked before any call), and `FakeReranker` is scriptable
  (scores, a typed error or `Hang` per call, calls recorded). The adapter bounds its own call by `RERANK_TIMEOUT_S`;
  the stage may still wrap any `Reranker` in its own scope (the fake's `Hang` exercises that). Nothing wires the
  reranker into `open_runtime` or the pipeline yet.
- The daily cap is reserved atomically in `daily_usage.rerank_calls` against `RERANK_DAILY_CAP`.
- On degradation: `rerank_used=false`, `rerank_error=<code>`, the RRF order is used. Log the reason (never silent,
  AGENTS.md §13).
- `latency_rerank_ms`, `meta.rerank_used`, shadow cost for rerank calls. `retrieval_config_hash` changes when rerank is on.
- `RERANK_TIMEOUT_S` (added in 6.02) bounds the stage; a timeout is a degradation, not an error of the request.
  `rerank_error` takes the codes of Tech §8 (`cap_reached`, `rate_limited`, `timeout`, `unavailable`, `rejected`,
  `bad_output`); the code goes to `request_logs.rerank_error` and the log, **not** to `AskResponse`/`Meta` (no API change).
- Shadow cost: `Pricing.require_rerank` (new, same rule as the other models: a missing or `unverified` price is a startup
  error when `RERANK_PROVIDER=cohere`) and `rerank_calls` in `shadow_cost`. The prices are already in `pricing.toml` (6.01).
- *As built (6.03):* the pipeline takes a `Reranker` and a `RerankCap` (`infra/budget.py`, the 5.05 pattern on
  `rerank_calls`); `open_runtime` builds both (no cap in eval mode, Tech §15.6) and tests inject a `FakeReranker`
  (`create_app(reranker=)`, `app_client(reranker=)`). The pipeline refuses a reranker that disagrees with
  `RERANK_PROVIDER` (the config hash keys the answer cache). Degradation catches `ProviderError` and `TimeoutError`
  only, so `CancelledError` and the request deadline pass; a failing reserve is fail-closed (`unavailable`); a degraded
  answer is not stored in the answer cache. `RequestTrace` carries `rerank_used`, `rerank_error`, `rerank_calls` and
  `rerank_model`, and the promptfoo result `metadata` copies the first two (6.04 reads them). Details: Tech §6, §8,
  §11, §14, §15.6; the decisions for the Author to veto: PRD §12 ("Phase 6 request path").
- **Nothing here switches rerank on anywhere hosted:** the Cohere Trial key may not be used in production (D55), so
  `RERANK_PROVIDER` stays `none` in every Vercel environment and no workflow gets `COHERE_API_KEY`. Tests use the fake
  reranker only.
- The UI does not change. It shows `rerank_used` in the collapsed debug row; a visible "rerank degraded" notice needs a
  `meta` field (an API contract change) and is an open item in PRD §12.
- Confidence: check that the Author's heuristic uses `rerank_score` when present. If it needs changing, that's the
  Author's code → **ask**. `CONFIDENCE_W_RERANK` stays `0.0`.
